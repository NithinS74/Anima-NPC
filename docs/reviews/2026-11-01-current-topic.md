# Current-question relevance and boundary scope

Reproduction: Daren answered a dragon-location follow-up and an unrelated Python-script request with a patrol-schedule refusal. The saved trace showed a real model_success, stale player patrol questions in history, guard boundaries in the profile, and irrelevant retrieval. It was not an error fallback. The current utterance appeared before history/evidence in the serialized user message, making old requests easy to confuse with the current one.

Plan/self-review (not independent): keep the current utterance last in the provider data message, explicitly scope restrictions to relevant current requests and require in-character ignorance for unsupported/out-of-world topics, and resolve simple pronoun follow-ups from an immediately preceding named-topic question before retrieval. Preserve the original utterance in model inputs and saved state; only the retrieval query is expanded. This is a bounded English heuristic with a previous-question fallback, not an autonomous topic/classifier system. Do not add topic-specific NPC replies, discard unrelated saved history, remove the guard boundary or add model calls.

Tests: requests with stale patrol history, a current unrelated question, actual boundary questions, simple named-person/plural-topic follow-ups, unchanged standalone queries and ambiguous previous utterances. Assert current-question placement, applicable policy and prompt-only history/data boundaries. Run full offline regression and bounded live Daren probes, report model-quality failures honestly.

Live review finding: clearer policy and question placement alone did not stop Nemotron from repeating the unrelated restriction. Resolution: add a narrow bounded lexical acceptance check for authored boundary topics fully repeated in an answer but absent from the current/resolved request. It rejects that answer and uses the existing one-repair path; it neither grants knowledge nor weakens boundaries. This is not a semantic/off-topic oracle and can miss paraphrases. Topic normalization is shared with retrieval. Repeated failure is explicitly surfaced as irrelevant_boundary, rather than silently accepting the unrelated response. No topic-specific generated line is built into runtime code.

Implementation self-review: the relevance check uses only trusted authored boundary text and the current/resolved request; unrelated older questions cannot make a restriction relevant. It does not strip boundaries or authorize disclosure. The check is English lexical overlap, not a semantic proof: paraphrases and ambiguous questions can be missed or misclassified. Repairs retain the same evidence, total deadline and two-call cap. A repeated mismatch returns an explicit irrelevant_boundary fallback. Current-question placement and pronoun rewriting preserve the original input and saved history. Condensed prompt policy preserved the existing small-budget evidence-packing regression rather than raising that test's budget.

Validation before final added repeated-failure case: 385 full offline tests passed; pip check, JavaScript syntax and diff whitespace checks passed. Live probes with an old patrol request in history produced no patrol-schedule refusal for the Python or dragon follow-up; an actual patrol-schedule request still refused disclosure. Python received a terse generic refusal; dragon retrieval now included the intended subject, but the model still presented a historical dragon-location passage as present-day guidance. That temporal grounding limitation remains open and is not concealed by these checks. Tests used disposable LabService instances without saved player-state writes. No canned topic answers were added to runtime code.
